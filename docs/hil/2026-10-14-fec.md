# HIL session 1, Part A: FE-C over BLE on the Tacx NEO (#44)

Part A of ADR-0002 §9: checks 1–4, the idle notification pattern, and every no-pedalling item from the
#204 and #206 checklists. Part B (pedalling, owner) is listed at the end.

| | |
|---|---|
| Date | 2026-10-14 |
| Trainer | Tacx Neo (DIS model `Neo`, firmware `0.7.4`), mains powered, nobody on the bike, no other central |
| Host | macOS, Apple Silicon, run from an Alacritty window (flock panes are denied Bluetooth by TCC) |
| Harness | `crates/crank-ble/examples/hil_fec` (feature `hil`), driver and transport from `crank-ble` |
| Captures | `docs/hil/captures/*.fecap` (both directions, `.fecap` format of #141) and `*.json` summaries |

## Method and limits

- One NEO, one firmware, one session. Replies are rare-loss events; rates below are from the stated sample
  sizes and are indicative, not tight.
- All frames, both directions, go through `crank_ble::Capture`; timestamps are µs on the harness's
  monotonic clock. Captures may interleave stamps (rx keeps its arrival time even when written after a later tx).
- Check 1, 2, 3 (values), 4 and the idle run use the real `BtleplugTransport` and the real `crank-fec`
  encoder; only the message envelope (message type, checksum rule) and, for write-without-response, the
  `hil`-gated hook `BtleplugTransport::write_without_response` differ from the production path.
  The latency calibration uses the real `FecTrainer` writer, pacer and capture unchanged.
- **Redaction.** Page 81 carries the device serial; the committed captures replace it with `FF FF FF FF`
  (checksum recomputed) and the summaries show the advertised name with digit runs masked and only an
  8-character platform-id prefix. Raw captures stay out of the repository (`hil_fec redact`).
- Precondition scan: the NEO advertised within the first seconds, so the run was not blocked.

How to rerun (from an Alacritty window; see AGENTS.md):

```text
cargo build -p crank-ble --features hil --example hil_fec
hil_fec scan | idle | check1 | check2 | check3 | latency | spacing | check4 | known --target <platform id>
hil_fec redact --target <raw .fecap> --out docs/hil/captures
hil_fec analyse --target docs/hil/captures/latency.fecap --out docs/hil/captures   # offline
```

## Idle notification pattern (no writes)

Sent: nothing; subscribe to `fec2` only, 60 s (`idle.fecap`, 228 records, `idle.json`).

Observed (frames per page, mean rate; gaps are consecutive arrivals of that page):

| Page | Count | Rate | Gap min / max |
|---|---|---|---|
| 25 (trainer data) | 166 | 2.77 Hz | 0.21 / 1.26 s |
| 16 (general FE) | 43 | 0.73 Hz | 0.24 / 2.52 s |
| 81 (product info) | 4 | sparse | up to 32.8 s |
| 80 (manufacturer) | 2 | sparse | |
| 250, 240, 251 (proprietary Tacx) | 4, 4, 3 | sparse | up to 32.8 s |

- The NEO interleaves its own pages at a combined rate of about 3.7 Hz, at the 4 Hz ANT message rate, with

- Pages 240/250/251 are unknown to the codec and surface as `Page::Unknown` (debug-logged). Not needed.
- Page 16 byte 1 bits 5–7: 0 in all 456 page-16 frames across the committed captures (type `0x19`).
- Messages are `0x4E` (broadcast) for pages 16/25 and `0x4F` for replies to requests.

## Check 1: checksum rule on writes (`check1.fecap`, `check1.json`)

Sent: page 70 request for page 54 (`A4 09 4F 05 46 FF FF FF FF 81 36 01 cc`) with four checksum bytes, three
rounds each, write-with-response, 0.5 s apart:

| Rule | `cc` | Answered (page 54) |
|---|---|---|
| XOR incl. sync (codec) | `17` | 3 / 3 |
| Sum excl. sync (pycycling, Tacx prose) | `57` | 3 / 3 |
| XOR excl. sync | `B3` | 3 / 3 |
| Wrong (XOR incl. sync ^ `FF`) | `E8` | 2 / 3 |

Observed: capture lines 2–12, e.g. `2523112 tx … 36 01 17` answered by `2585814 rx A4 09 4F 05 36 FF FF FF FF C8 00 07 1E`.
The one unanswered request is one of the rare lost replies (see check 3); another earlier run of the same
check answered 3 / 3 for the wrong rule.

Conclusion: the NEO does not validate write checksums. The Tacx prose and the worked example disagree, and
both are accepted; XOR incl. sync stays the encoding because it is what the NEO itself sends (all 3063 rx
frames in the committed captures verify under it). Confirms ADR-0002 §4.1; note added there. Not relied on.

## Check 2: message type and write response (`check2.fecap`, `check2.json`)

Sent, per cell × 3 rounds (XOR checksum): (a) page 70 request for page 54; (b) page 49 at 110/120/…
W, 0.3 s later a request for page 71. Cells: type `0x4F` / `0x4E` × write with / without response.

| Cell | request(54) answered | page 49 echoed by page 71 |
|---|---|---|
| `0x4F` + response (production) | 3 / 3 | 3 / 3 |
| `0x4F`, no response | 3 / 3 | 3 / 3 |
| `0x4E` + response | 3 / 3 | 3 / 3 |
| `0x4E`, no response | 2 / 3 | 3 / 3 |

(One page-54 request in the last cell went unanswered; all 12 page-71 requests were answered. The control
write was applied in every cell: the echo matched.)

Conclusion: the NEO accepts both message types and both GATT write modes. ADR-0002 §4.1 (`0x4F`, with
response) is confirmed and unchanged. Write-without-response is a possible latency option for later, not
needed.

## Check 3: page 71 (`check3.fecap`, `check3.json`)

Sent (all `0x4F`, XOR, with response): a request for page 71 before any control page; page 70 with
`times` 1, 0, 3; then each value below followed 0.3 s later by a request for page 71 (retried once if
unanswered, recorded). Then 8 alternating page-49 writes and 8 bare requests for the sequence byte.

Page 71 layout as seen: `A4 09 4F 05 47 <last page> <sequence> <status> <echo 4–7> cc`.

| Sent | Echo (bytes 4–7) | Status | Reading |
|---|---|---|---|
| (before any control) | `FF FF FF 00`, last page `0x30` | 0 | power-on state reads as resistance 0 %, `00` = 0 %. Not a disagreement |
| 49: 100 W (`90 01`) | `FF FF 90 01` | 0 | exact |
| 49: 200.25 W (`21 03`) | `FF FF 20 03` | 0 | **200 W**: 0.25 W bits dropped |
| 49: 200.5 W (`22 03`) | `FF FF 24 03` | 0 | **201 W**: rounded to whole watts |
| 51: 0 %, Crr 0.004 (`20 4E`, `50`) | `FF 20 4E 50` | 0 | exact |
| 51: 5 %, Crr 0.004 (`14 50`, `50`) | `FF 14 50 50` | 0 | exact |
| 51: Crr `0xFF` (0.01275) | `FF 20 4E 50` | 0 | **ignored**: previous Crr `0x50` kept |
| 50: 0.51, 0 km/h, 1.0 | `FF 33 7F 64` | 0 | exact |
| 50: 1.86, +127 km/h, 1.0 | `FF BA FE 64` | 0 | exact (applied as numbers) |
| 48: 50 % (`64`) | `FF FF FF 64` | 0 | exact |
| 48: 100 % (`C8`) | `FF FF FF C8` | 0 | exact (applied as a number) |
| 55: 75 kg, 10 kg, 708 mm | last page still `0x30`, echo `FF FF FF C8` | 0 | page 55 **not** echoed |
| 49: `0xFFFF` (16 383.75 W) | `FF FF 00 00` | 0 | **invalid**: target replaced by 0 W |

Capture offsets: 200.25 W tx at 15981131 (line 68) → rx 16382420 (line 71); 200.5 W → 17102101 (after a retried
request); Crr `0xFF` rx 19263478; 0xFFFF tx 25434085 → rx 25863564 (`check3.fecap` lines 68–71, 74–77, 95, 137–141).

Sequence byte (byte 2 of page 71): increments by **1 per control page (48–51) and per page-70 request** the NEO
receives, modulo 256 (wraps `FF → 00`, seen at lines 107–113), and not for page 55:

- per control write + request: 9, 11, 13, 15, 17, 19, 22, 24 (+2 each; one +3 where an unanswered request was
  also received);
- per bare request: 25, –, 27, 28, 29, 30, 31, 32 (+1 each; the missing one is a lost reply, and the next
  value shows the request was received).

Page 70 `times` (one trial per count, n = 1): 1 → 1 page-54 reply, 3 → 3 replies, **0 → 5 replies** within
0.82 s of the request (lines 26–31: request at `7130862`, replies at `7202663`, `7202963`, `7440749`,
`7680914`, `7950883`: an immediate pair, then one per ~0.24 s), then none in the remaining 3 s of the window.
Consistent with "repeat until acknowledged" with a cap of about five, but one trial establishes neither the
cap nor that it is not time-limited.

Lost replies, counted by sequence number (`hil_fec analyse`, `*.analysis.json`; an earlier version of the
harness counted page-71 *frames* and so hid losses behind the `0x4E` copies described next). A request is
lost when no reply carries its sequence number; every reply that does arrive did so within 0.12 s (n = 317 in
the driver run, so a reply is never "answered by the next poll"):

| Capture | Requests for page 71 | Never answered |
|---|---|---|
| `check2` | 12 | 0 |
| `check3` | 32 | 3 |
| `spacing`, one request after another (250 / 500 / 1000 / 2000 ms apart) | 79 with a known gap | 5 (2 of 19, 0 of 19, 3 of 19, 0 of 22) |
| `spacing`, 0.1–1 s after a control write | 40 with a known gap | 4 |
| `latency`, the driver's 1 s polls | 344 | 27 (7.8 %) |

No dependence on spacing, envelope or delay could be established. The effect sets the latency tail below.

Repeated replies. 80 of the 397 page-71 frames in the driver run are `0x4E` (broadcast) copies of a `0x4F` reply
with the same sequence and bytes (7 of 118 in `spacing`, 1 each in `check2` and `check3`): 66 of the 80 arrive
within 1 ms of the original, the others up to one 4 Hz slot (0.24 s) later. A reply is therefore not always
`0x4F` and copies are not batched with their original. Each copy becomes its own `Observed` event in the
driver; ADR-0002 §4.4 explains why that is harmless to the following machine.

Unsupported page requests. A page-70 request for page 16 or 25 (check 4) is answered by page 71, last page
`0x10` / `0x19`, status 2 (not supported), echo `FF FF FF FF` (`47 10 DD 02 FF FF FF FF`, `check4.fecap` lines
48–50 and 54–55). It overwrites the last-page field that the following machine reads.

Conclusions:

- The §4.4 **hardware gate passes**: page 70 → page 71 works and bytes 4–7 of pages 48–51 are echoed exactly
  (modulo the invalid values); `Observed` can come from page-71 echoes, `trainer_following` is not
  permanently `unknown`.
- The sequence byte **does** increment verifiably (by 1 per control/request message); the gated enhancement
  (command-specific correlation) is feasible and remains an ADR amendment for later. v1 unchanged.
- Page 49 has **1 W** resolution on the NEO. §7.1's 1 W grid is therefore the true control resolution;
  `grid_key()` comparisons stay exact because the engine emits whole watts.
- **0xFFFF and Crr 0xFF are not numeric on the NEO** (contradicts §4.2's "kept as numeric values, not
  sentinels"): amended; `encode` still accepts them (#215).
- Page 55 does not touch page 71's last-page/echo; the §4.4.1 routing rule R1 (page-55 echoes are neutral)
  needs no change, since the NEO never produces one.

### Calibration of `L`, `T_unknown` and the SIM echo schedule (`latency.fecap`, `latency.analysis.json`, `spacing.analysis.json`)

What `L` bounds (architect decision on #44): the **age of a stale echo**, an echo of a value that a newer
desired value has superseded (rule R2). It is not the latency of the first echo of a new value. Both were
measured.

Method: the real `FecTrainer` (connect sequence: page 55, request 54), `SetMode` commands issued through its
control channel, and its own 1 s page-71 polls, about 6 min. Changes were spread over every phase of the poll
grid (a deterministic 0–1 s jitter: an earlier run with evenly spaced changes sampled one phase only).

**Stale echoes** (`hil_fec analyse`, `stale_echoes`): of the 397 page-71 frames, 2 echoed a value that had
already been superseded by a write, both ERG, 16.2 ms and 22.4 ms after the write of the new value; none for
SIM track (30 changes) or wind (not changed). The desired change precedes the write by the writer delay, at
most 0.5 s nominal / 0.75 s worst case (§4.4, driver tests of #43), during which polls still read the old
value; so the stale-echo age from the desired change is at most 0.75 + 0.022 ≈ 0.8 s, against `L` = 2 s. The
SIM wind component's stale-echo age was not exercised (wind unchanged); see Part B.
(`check3`'s one "stale" echo, 1.12 s, is the Crr `0xFF` write the NEO ignores: the echo equals an earlier
value, not a late reply.)

**First-echo latency** (from the `SetMode` call to the first `Observed` echoing the new value):

| Mode | n | min | p50 | p90 | max | over 2 s | never echoed |
|---|---|---|---|---|---|---|---|
| ERG 100 ↔ 150 W | 60 | 0.29 s | 0.81 s | 1.27 s | **2.19 s** | 2 | 0 |
| SIM grade 1 ↔ 2 % (track echo; wind unchanged) | 30 | 0.34 s | 1.60 s | 2.71 s | **4.21 s** | 6 | 0 |

A second full run with the final harness gave ERG max 2.07 s (2 of 60 over 2 s) and SIM max 4.26 s (4 of 30
over 2 s), no missing echoes, no faults (not committed; same logic). Only the SIM *track* component was
calibrated; the wind echo schedule was observed (below) but no wind change was made.

- Reply gaps from distinct `0x4F` replies, driver run: ERG median 0.99 s (max 2.04 s; 7 gaps above 2 s, each a
  lost reply). SIM per component: page 50 n = 61, page 51 n = 63, median 2.01 s, max 4.05 s, 6 gaps above 3 s
  each. Replies alternate between page 50 and 51 as the §4.4.1 schedule requires. (The earlier "gaps" of
  12 µs and 193 µs were `0x4E` copies, not replies.)
- Reply latency when a reply arrives: p50 0.06 s, max 0.12 s (n = 317).

Check against the §4.4.1 constants (nothing else changes unless contradicted):

- `L` = 2 s: stale-echo age ≤ ~0.8 s. **Confirmed**.
- `T_verify` = 2 s: independent of first-echo latency (span of the agreeing replies). Unchanged.
- Reply periods `P_c` = 1 s (ERG) and 2 s (SIM): measured medians 0.99 s and 2.01 s. Confirmed.
- `T_unknown`: a flat 5 s **is contradicted for SIM** and is replaced by the per-component
  `T_unknown(c) = 4·P_c + 1 s` (5 s ERG and resistance, 9 s SIM track and wind). No component went silent
  in the run (largest gap 4.05 s, largest first echo 4.21 s), but silence is a gap of `(m + 1)·P_c` after
  `m` consecutive lost replies, and the measured loss rate (p = 27/344 = 7.8 % of the driver's polls;
  5–10 % in the other captures, up to 9.4 % in `check3` and 10 % just after a control write) makes that
  likely at 5 s for SIM: with independent losses a run of `m` starts at `3600/P_c · p^m` per hour, where
  `m = ⌈T_unknown/P_c⌉ − 1`.

  | `T_unknown` | ERG (P = 1 s) | SIM component (P = 2 s) |
  |---|---|---|
  | flat 5 s | m = 4: 0.14 / h | m = 2 (gap 6 s): `p²·3600` = **22 / h** |
  | 4·P_c + 1 s | 5 s, m = 4: 0.14 / h | 9 s, m = 4 (gap 10 s; three losses = 8 s tolerated): 0.14 / h |

  At p = 10 % the new rule gives 0.36 / h, at p = 4 % (bare requests) 0.01 / h. Independence is an
  assumption: the 27 losses were all isolated (no two requests in a row; independence expects 2.1 adjacent
  pairs, probability of none 0.12), and in the SIM phase no two replies of the same component were lost in
  a row (135 requests, 0.82 expected, probability of none 0.44). The sample cannot reject independence or
  establish it. Part B counts `silent` episodes of a healthy NEO over a long SIM ride and amends the rule if
  they exceed the rate above. Reproduce: `hil_fec analyse` (`lost_run_lengths`, `independence`).
- `T_decide(c)` (7 s ERG, 10 s SIM) does not depend on `T_unknown` and is unchanged: the model's fair walks
  (replies every `P_c`) reach a maximum of 6 s and 10 s. Guarantee 7 (a silent trainer shows `checking`)
  becomes 5 s for ERG and 9 s for SIM; guarantees 1 and 4 are unchanged.

## Check 4: pages 54, 80, 81, 55 (`check4.fecap`, `check4.json`)

Sent: page 55 (75 kg, 10 kg, 708 mm: `37 4C 1D FF 88 0C 46 00`, the #70 layout), then page 70 requests for

| Page | Observed (all identical across repeats) | Reading |
|---|---|---|

| 81 | `51 FF 00 07 <serial>` | supplemental revision 0, main software revision 7 (DIS firmware `0.7.4`), serial present (redacted) |
| 55 | `37 4C 1D FF 88 0C 46 00` | read back byte for byte: 75.00 kg, 10.00 kg, coarse 70 + nibble 8 = 708 mm, gear ratio 0 |
| 55 with nibble 10 / 12 / 14 | echoed unchanged (`8A`, `8C`, `8E` in byte 4) | stored and reported verbatim |
| 55 with nibble 15 (`0xF`) | reported as `0` | `0xF` normalised |
| 16, 25 (request) | page 71 with last page `0x10` / `0x19`, status **2 (not supported)**, echo `FF FF FF FF` (`47 10 DD 02 FF FF FF FF`) | an unsupported request overwrites page 71's last-page field (above). The harness waited for a page-16/25 reply, so the summary shows none; the frames are in `check4.fecap` lines 48–50 and 54–55 |

Conclusions: the §4.2 layouts for pages 54, 80, 81 and 55 are confirmed on a NEO; the corrected #70
wheel-diameter packing is accepted (708 mm gives byte 6 = 70 and nibble 8, exactly as sent); the NEO
stores nibbles 10–14 and gives no sign they are invalid, so decoding them as `None` stays a codec policy
(still tentative). Page 54's maximum resistance is a plain number on this NEO. Requests for pages 54/55/80/81
were answered 12 of 12 in the committed run.
